# Precedent and implementation approach for physics-informed on-policy fine-tuning and friction-cone projection layers

## KQ1: What's existing precedent for physics-informed/semi-supervised fine-tuning using physics-residual losses on unlabeled, self-collected (on-policy) data -- in robotics or adjacent ML literature?

### Takeaway
The closest verified precedent is the Posa-lab adaptive contact-implicit MPC work (arXiv 2310.09893): it learns a residual on a physics-based contact model in real time, using *only* observed state transitions from the controller's own closed-loop behavior (no ground-truth labels), and reports a jump from 0% to ~90% task-initiation success with adaptation on hardware. A second, larger-scale pattern match is LIFT (arXiv 2601.21363, ICLR 2026), which deploys a deterministic policy in the real/new environment to collect data while confining stochastic exploration to a learned world model -- structurally the same "collect on-policy states in the real loop, do the risky/exploratory learning inside a model" idea as this project's idea 2. No paper was found doing this specifically for tactile/fingertip slip prediction, which is a genuine gap (and supports novelty) rather than a dead end.

### Cited Findings
- Huang, Aydinoglu, Jin, Posa, "Adaptive Contact-Implicit Model Predictive Control with Online Residual Learning": the method learns a residual term `r_comp` "adaptively at real-time rates to compensate the error" on top of a prior linear-complementarity-system (LCS) contact model — [arXiv 2310.09893](https://ar5iv.labs.arxiv.org/html/2310.09893)
- The loss is a QP-based "implicit loss" comparing the prior model's predicted next state to the observed next state (`z = A·x_k + B·u_k + d* − x_{k+1}`); it uses only observed transitions `{x_{k+1}, x_k, u_k}` and the prior model's matrices — no ground-truth labels are required — [arXiv 2310.09893](https://ar5iv.labs.arxiv.org/html/2310.09893)
- Data comes from the controller's own closed-loop/on-policy behavior: the MPC "uses the latest residual value `r_comp`" when computing its control input, and the buffer holding recent transitions used n_b = 10 points on the hardware experiment — [arXiv 2310.09893](https://ar5iv.labs.arxiv.org/html/2310.09893)
- Reported results: on a hardware ball-rolling task, the controller "adapt[s] and compensate[s] well within around 10 pushing trials for model errors up to 8 mm"; on fruit-rolling (orange/lime, 20 trials each) the method achieved ~90% success at initiating tracking vs 0% without adaptation, with full-circle completion rates of ~70% (orange) and ~50% (lime) — [arXiv 2310.09893](https://ar5iv.labs.arxiv.org/html/2310.09893)
- Update mechanics in the paper are internally inconsistent: body text says updates use "a simple gradient step (via learning rate ξ)" while Algorithm 1 says "Update the residual `r_comp` via Adam" — worth noting if replicating, since it is unclear which was actually used — [arXiv 2310.09893](https://ar5iv.labs.arxiv.org/html/2310.09893)
- LIFT (ICLR 2026): a three-stage framework — large-scale off-policy SAC pretraining in simulation, a physics-informed world model, and fine-tuning where "data collection in the new environment executes a deterministic policy" while "stochastic exploration is instead confined to a physics-informed world model" — [arXiv 2601.21363](https://arxiv.org/abs/2601.21363)
- Secondary summaries (not independently verified against full primary text, since the PDF could not be parsed and the abs page lacks detail) describe the LIFT world model as pairing Lagrangian dynamics with a residual predictor absorbing contact forces/unmodeled effects, and report that an ablation removing SAC pretraining caused near-zero forward speed — [besthub.dev summary](https://www.besthub.dev/tags/lift); [Korean-language review](https://liner.com/ko/review/towards-bridging-the-gap-between-largescale-pretraining-and-efficient-finetuning)
- TAM (Torque Adaptation Module): applies DAgger-style fine-tuning where rollouts are collected and training is driven by an analytic physics-based teacher-torque objective computed in simulation; the real robot "needs no weight updates or teacher labels" at deployment time — but note the sim-side teacher still supplies an explicit physics signal, so this is only a partial match (adaptation happens in sim before deployment, not from unlabeled real on-policy data) — [arXiv 2606.06218](https://arxiv.org/pdf/2606.06218)
- PhyFilter explicitly frames the "no labels at deployment" problem: "during deployment no ground-truth labels are available, so the residual cannot be obtained instantly," and positions itself as a correction module deployable directly on a pretrained model without retraining, using real-time state feedback plus a priori dynamics structure — [besthub.dev](https://www.besthub.dev/articles/phyfilter-physics-based-feedback-lets-robots-generalize-without-massive-data-60b69afc90fe); related preprint "Physics Filtering Favors the Generalization of Robot Learning" — [arXiv 2608.22701](https://arxiv.org/pdf/2608.22701)
- A caution directly relevant to staged fine-tuning: a PDE-modeling paper fine-tunes a transition module with physics loss alone first, then the encoder with labeled loss, and found that "the fine-tuned transition module mismatches [the] encoding module now, leading to deteriorating performance in general" when staged in the wrong order — [arXiv 2412.09116](https://arxiv.org/pdf/2412.09116)
- A constraint-aware PINN for continuum robots down-weights the physics loss term during fine-tuning on real experimental data, using α_phys = 0.05, specifically "to allow adaptation to the experimental measurements" — a concrete precedent for how to balance a physics-residual term against other signals during fine-tuning — [arXiv 2608.26273](https://arxiv.org/pdf/2608.26273)
- A general survey of physics priors in robot learning cautions that a small physics-loss training residual "does not necessarily guarantee exact satisfaction of the governing equations at inference time," and separately catalogs residual-learning approaches (e.g., an MLP learning residuals of a physics-based feedforward controller, regularization pulling learned parameters toward physical values) — [arXiv 2609.22319](https://arxiv.org/pdf/2609.22319)

### Inferences
- The Posa-lab paper is the strongest direct template for idea 2: it is label-free, on-policy, physics-residual-based, hardware-validated, and reports a dramatic (0%→90%) success-rate gain from the adaptation loop — this validates that the already-decided idea 2 plan (train baseline → run closed loop → collect visited states → fine-tune with physics-residual loss only → repeat) is not a speculative approach but matches a published, working pattern in a closely adjacent contact-dynamics domain.
- Given the project's own diagnostic finding (tactile sums are flat between slip/stable trials, pull_force shows the clean pre-slip rise), the physics-residual loss used for idea 2's fine-tuning is more likely to succeed if it is built on a whole-hand force/torque-balance residual (consistent with the previously-deferred Newton's-second-law idea) rather than reintroducing a per-fingertip Coulomb-ratio-style feature, since the per-fingertip version was already extensively tested and shown non-discriminative. The precedent above (Posa lab's residual is a *whole-system* state-transition residual, not a per-contact ratio) supports pursuing the aggregate/whole-hand framing over a per-fingertip one.
- The staged-fine-tuning-order caution (arXiv 2412.09116) suggests that if the project's fine-tuning touches multiple sub-modules (e.g., a shared TCN trunk plus a physics-residual head), the order in which physics-only vs. labeled-loss updates are applied should be chosen deliberately and perhaps tested both ways on a small scale, rather than assumed safe.

### Gaps
- Could not access the full primary text of LIFT (arXiv 2601.21363) beyond the abstract — the PDF was an unreadable binary stream via WebFetch, and the architecture/ablation claims above rely on secondary summaries (besthub.dev, a Korean-language third-party review) that should be verified against the actual paper (or its HTML version at arxiv.org/html/2601.21363v3) before being cited as fact in a final report.
- Could not verify PhyFilter / "Physics Filtering Favors the Generalization of Robot Learning" beyond search-snippet level detail; the arXiv ID appeared inconsistently across sources and full methodology (e.g., exact loss form, whether it's truly label-free fine-tuning vs. a fixed filter) is unconfirmed.
- No paper was found applying this on-policy/physics-residual fine-tuning pattern specifically to tactile sensing or slip prediction — all strong precedent is from locomotion or rigid-body contact-manipulation (ball/fruit rolling), not fingertip tactile force time series. This is a translation the project would be doing itself, not following directly.

## KQ2: What's the simplest correct way to implement a differentiable projection onto a friction cone, and what pitfalls exist (e.g. gradient behavior at the cone boundary)?

### Takeaway
A fully closed-form, 3-case piecewise projection formula onto the Coulomb friction cone exists and is directly implementable in PyTorch with `torch.where` (no iterative solver needed) for the scalar-normal + vector-tangential case; the real pitfall is not the forward projection but the backward pass — multiple 2026 papers independently report that hard/orthogonal projection layers produce rank-deficient or ill-behaved Jacobians near the constraint boundary, which can stall gradient flow into the upstream network.

### Cited Findings
- Closed-form Coulomb cone projection (primal-dual quasi-static contact paper), Eq. 26 / Algorithm 3: for a force vector `(s_n, s_t)`, `Π_F(s_n, s_t) = max{0, λ1}·ξ1 + max{0, λ2}·ξ2`, with `λ1 = -μs_n - ‖s_t‖`, `λ2 = -s_n + μ‖s_t‖`, and case logic: (1) if `λ1 ≥ 0` the point is already inside the cone and is returned unchanged; (2) else if `λ2 ≤ 0` the projection is the apex `(0, 0)`; (3) else the projection lands on the cone boundary via `λ2/(1+μ²)·(-1, μ·s_t/‖s_t‖)` — [arXiv 2101.11763](https://ar5iv.labs.arxiv.org/html/2101.11763)
- At `μ = 1` this formula "corresponds to a formula of the projection onto the second-order cone," derived via spectral factorization in a Jordan algebra — i.e. the friction-cone projection is a generalization of the standard SOC projection — [arXiv 2101.11763](https://ar5iv.labs.arxiv.org/html/2101.11763)
- The source paper does not discuss differentiability or gradient behavior at the boundary/apex at all — it only gives the piecewise forward formula, so any gradient analysis must come from other sources — [arXiv 2101.11763](https://ar5iv.labs.arxiv.org/html/2101.11763)
- A 2026 paper on projection layers argues standard orthogonal projections "produce rank-deficient Jacobians that block gradients," and proposes a radial mapping into the interior of the feasible region as a fix instead of an exact boundary projection — [arXiv 2602.03461](https://arxiv.org/pdf/2602.03461)
- A May-2026 paper states existing cone-projection gradient methods "rely on strong assumptions that can fail in practice," and proposes a cheaper, more robust Jacobian specifically for linearly-constrained networks — [arXiv 2605.11526](https://arxiv.org/pdf/2605.11526)
- Donti, Roderick, Fazlyab, Kolter build a custom differentiable solver for projection onto second-order cones specifically because "that projection has no closed form" in their more general multi-constraint policy setting — implying that once constraints couple across multiple fingertips/cones simultaneously (rather than one independent cone per fingertip), a closed-form approach may no longer suffice and an implicit/iterative differentiable solver becomes necessary — [arXiv 2011.08105](https://arxiv.org/pdf/2011.08105)
- cvxpylayers (Agrawal, Amos, Barratt, Boyd, Diamond, Kolter) is the standard general-purpose library route for a differentiable convex projection (including second-order cones) via implicit differentiation of the KKT conditions, but a 2026 blog post notes it "has not been maintained since about 2024" — a compatibility risk worth checking before adopting it under a tight deadline — [Towards Data Science](https://towardsdatascience.com/how-to-encode-constraints-to-the-output-of-neural-networks-9bce302b9687)
- Πnet uses operator splitting for the forward projection and the implicit function theorem for the backward pass, for general convex-constraint projection layers — a heavier general-purpose alternative, found via search only (not independently fetched for implementation depth) — [arXiv 2508.10480](https://arxiv.org/pdf/2508.10480v1)
- A smoothed/regularized alternative to a hard projection exists in the optimal-control literature: Capobianco & Leyendecker regularize the set-valued Coulomb friction law with a projection that "yields differentiable equations for optimal control," fitting a pendulum-with-frictional-clutch benchmark better than a sigmoid regularization while still reproducing exact sticking — a middle-ground option between a soft loss penalty and a hard non-smooth projection — [DOI 10.1002/pamm.70060](https://www.alphaxiv.org/abs/2607.19599.md) (PAMM 2026; also referenced via conference listing)
- Quantified evidence that hard constraints hold up better than soft penalty losses over long rollouts (a directly relevant precedent for the project's planned soft-loss-vs-hard-projection comparison): on a damped-pendulum benchmark, a hard-constrained DeepONet cut normalized RMSE after 100 time steps from ~6.5×10⁻² (soft penalty) to ~1.7×10⁻² (hard constraint), averaged over 10 runs per setting — [arXiv 2309.07899](https://arxiv.org/pdf/2309.07899)
- DiffSDFSim approximates a spherical friction cone with an 8-direction polyhedral cone specifically so that friction Jacobians become computable — another concrete, simple pattern (polyhedral approximation) for sidestepping exact-cone non-smoothness — [arXiv 2111.15318](https://arxiv.org/pdf/2111.15318)

### Inferences
- For this project's scale (one scalar friction coefficient `mu_combined` already as an input feature, and prior failed features already reduced per-fingertip force pairs down to normal/tangential magnitudes), the single-cone closed-form formula above is almost certainly sufficient — there is no need for cvxpylayers, Πnet, or a custom QP solver, which would add dependency and debugging risk unsuited to a tight March deadline and a high-schooler's PyTorch experience level. A student-tractable implementation is: predict `(normal, tangential)` force components per fingertip from the TCN, apply the 3-branch `torch.where` projection above per fingertip (or aggregated, matching the existing min/sum-across-5-fingertips structure from prior experiments), independently for each fingertip since each cone is independent (no cross-fingertip coupling needed at this scope).
- Because the source formula's own `ξ1` term did not pass an independent algebraic check (it should lie exactly on the cone boundary only when μ=1, which should not be a special-cased requirement of a general μ formula), it should be re-derived from the cone definition (`‖s_t‖ ≤ μ·s_n`) directly rather than copied verbatim — this is a concrete implementation risk to flag for the student rather than silently trusting the cited paper.
- Given the rank-deficient-Jacobian pitfall reported in two independent 2026 papers, the "hard projection" variant should be instrumented to check gradient norms flowing back into the pre-projection TCN output during training (e.g., log `grad_norm` at the layer boundary) rather than assuming it trains normally; if gradients vanish or destabilize training, the Capobianco–Leyendecker-style smoothed/regularized cone (soft but bounded, rather than a hard max/min projection) is a documented, differentiable-everywhere fallback that still approximates a hard constraint.
- The hard-vs-soft RMSE-over-rollout result (arXiv 2309.07899) suggests the right metric for comparing idea 3's variants is not single-timestep loss but degradation over a rollout/trial horizon — directly supporting the project's own framing of comparing variants by closed-loop control failures rather than static per-timestep accuracy.

### Gaps
- No paper was found implementing a friction-cone projection layer specifically inside a learned tactile/slip-prediction network (as opposed to classical contact-mechanics solvers, grasp-synthesis optimizers, or robot-arm control policies) — this is a genuine translation step the project would be doing itself, not one with a direct template to copy.
- Could not independently verify the Donti et al. (arXiv 2011.08105) paper's exact mechanism for backpropagating through their second-order-cone solver (e.g., implicit function theorem vs. unrolled iterations) — the PDF was unreadable via WebFetch, so this detail comes only from a WebSearch synthesis snippet, not a direct quote.
- Could not confirm whether the closed-form projection, when applied per-fingertip independently and then the outputs combined (e.g., summed) for a trial-level slip decision, preserves good gradient behavior through the combination step — none of the sources address a multi-cone-then-aggregate architecture specifically.

## KQ3: Given this project's closed-loop system already exists (MuJoCo-based, with predict_slip()/decide_action() integration points), what's a concrete, scoped-down version of comparing no-physics / soft-loss / hard-projection variants in terms of closed-loop control FAILURES specifically?

### Takeaway
Published closed-loop slip-control evaluations are small-scale (10-100 trials), use inconsistent sensors and protocols, and are not directly numerically comparable to each other -- but several of them converge on a useful failure *taxonomy* (missed-slip/drop, false-alarm, and control-induced failure) that this project can adopt as its own fixed, internally-consistent protocol across the three model variants, rather than trying to benchmark against published numbers.

### Cited Findings
- Evetac (event-based optical tactile sensor): across 10 trials per object, closed-loop slip-triggered pickup control reached 93% overall success, while skipping closed-loop control entirely produced zero successful lifts in the control condition — framed by the authors as evidence that slip detection *plus* control, not detection alone, is what matters, and that failures can stem from the detection/control interplay rather than detection error alone — [arXiv 2312.01236](https://arxiv.org/pdf/2312.01236)
- SlipSense (multimodal tactile slip detection): on 100 operator-induced slip trials on unseen objects, detection caught every slip event with no false alarms, and the controller prevented object loss in 95 of 100 trials; critically, the 5 failures were attributed to the prevention/corrective motion itself (inward finger motion pushing the object out) rather than to missed detection — an explicit "control-induced failure" category distinct from "missed-detection failure" — [arXiv 2609.15910](https://arxiv.org/pdf/2609.15910)
- GelSight slip-detection-with-regrasp: across 99 grasp trials, the robot ended with a stable grasp in 88 (~89%); failures were linked specifically to grip forces too small for the sensor to measure slip reliably — i.e., failures clustered in a specific physical regime (low grip force) rather than being uniformly distributed — [arXiv 1708.00922](https://arxiv.org/pdf/1708.00922)
- Center-of-mass-based robust grasp planning: closed-loop policies using slip feedback outperformed open-loop baselines over 20 grasps per object per policy, and the authors explicitly count *false* slip predictions as failures too, not just missed slips — reinforcing a two-sided failure taxonomy (miss vs. false alarm) — [arXiv 2006.00906](https://arxiv.org/pdf/2006.00906)
- Learned contact-event detection on vision-based tactile sensors: success rate rose from 46% (no contact detection) to 98% (with it) across 10 objects × 10 trials — a contact-detection rather than pure slip-control result, but it establishes that a no-physics/no-detection baseline condition (comparable to this project's "no-physics" variant) is a standard and informative control arm — [arXiv 1910.03973](https://arxiv.org/pdf/1910.03973)
- Explicit caveat on cross-paper comparability: these results "use small trial counts, different sensors, and different definitions of failure" and there is no standardized benchmark; a reliable failure-rate comparison requires reading each paper's full protocol rather than taking headline numbers at face value — [synthesis across arXiv 2312.01236, 2609.15910, 1708.00922, 2006.00906, 1910.03973]

### Inferences
- Because no standardized benchmark exists, the project should define its own fixed, internally-consistent protocol applied identically across all three variants (no-physics baseline, soft physics loss, hard friction-cone projection) rather than trying to match published failure rates — this is actually an advantage for an ISEF project, since the comparison is self-contained and controlled.
- A scoped protocol consistent with the precedent above: run on the order of 100 closed-loop trials per variant (matching SlipSense's scale, well within reach of a MuJoCo sim rather than real hardware), using a fixed, varied set of pull-force ramp profiles and `mu_combined` values that deliberately include a low-friction/near-failure regime — since GelSight's finding (failures cluster at low grip force) suggests this is exactly the regime where a hard friction-cone projection should matter most and a no-physics baseline should struggle most.
- Log a failure taxonomy per trial rather than a single pass/fail bit, mirroring the categories that recur across the cited papers: (1) missed-slip → object drop (detection failure), (2) false-positive → unnecessary grip tightening (false-alarm, per the CoM-grasp paper's explicit inclusion of false predictions as failures), (3) control-induced failure (the corrective action itself causes the failure, per SlipSense's 5/100 cases) — reporting per-variant breakdowns of these categories (not just an aggregate success rate) directly supports the project's framing of comparing variants "in closed-loop control-failure terms, not just static accuracy," and gives a richer, more defensible result for an ISEF judge than one aggregate number per variant.
- Given the existing `closed_loop_sim.py` already has `predict_slip()`/`decide_action()` integration points, the scoped implementation is likely: swap in each of the three model variants behind the same `predict_slip()` interface, keep `decide_action()` and the trial/ramp-profile generation fixed across all three runs, and add trial-level logging of (slip ground truth from the simulator, model prediction, action taken, outcome category) — this reuses the existing harness rather than building new infrastructure, which matters given the "not full-time" time budget.

### Gaps
- No source gave a standardized or recommended number of trials, nor a statistical-significance guideline, for comparing closed-loop grasp-control variants — trial counts in precedent (10, 20, 99, 100) appear to be pragmatic/hardware-time-driven rather than power-analysis-driven, so the project will need to pick its own trial count (likely larger than hardware-constrained prior work, since it's pure simulation) without a citable justification from this literature.
- None of the cited closed-loop papers evaluate a friction-cone-projection variant specifically (hard-projection vs. soft-loss vs. no-physics) — the taxonomy and protocol structure above is adapted from slip-detection/control papers in general, not from any paper running this exact three-way comparison, so the specific comparison design is this project's own contribution rather than a literature-verified protocol.
- Could not find any precedent for evaluating failures *stratified by physical regime* (e.g., explicitly binning trials by friction coefficient or pull-force ramp rate and reporting failure rate per bin) as a formal method, even though GelSight's finding suggests this would be valuable — the recommendation to stratify by low-mu/near-failure regime is an inference from a single incidental finding, not a tested methodology.
